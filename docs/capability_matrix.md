# Capability and acceptance matrix

This is the acceptance ledger for SED's JKDF2, MotS, IJIM, and DroidWorks editor work. It is a coverage inventory, not a claim that every listed capability already works. A feature is complete only when its applicable evidence layers pass or Andrei explicitly records a waiver with scope and rationale.

## Evidence rules

- **documented**: a manual, changelog, tutorial, video, or audit records a capability; this does not establish compatibility.
- **source-inspected**: implementation or authoritative reference source was inspected at the named revision; this does not establish a passing test.
- **structurally-tested**: a freshly executed check covers parsing, editing, serialization, state, refusal, or another nonvisual contract.
- **visually-tested**: actual rendered output or interactive behavior was inspected; an editor screenshot is not game acceptance.
- **runtime-tested**: the actual target game loaded the modified level and the scenario's causal/runtime checks passed.
- **missing**: the required implementation or artifact is absent.
- **inaccessible**: no usable executable/source/artifact was recovered; the historical capability remains documented but cannot be claimed tested.
- **waived**: Andrei explicitly accepted a bounded exclusion. No row is waived by default.
- **pending**: evidence has not been freshly collected. Historical test totals are provenance, never current Qt acceptance.

The old-fork F-rows derive from [the Coda inventory](port/CODA_FEATURES.md), including its refusal, provenance, and non-claim boundaries. D-rows derive from [the later delta inventory](port/DELTA_INVENTORY.md). Pascal P-rows derive from [the reachable-entry-point audit](porting_guide.md#verified-live-pascal-gaps). Plugin E-rows derive from the preserved `JED_SED_PLUGIN_AUDIT_20260930.md` and its machine-readable catalog in the external research checkout. Editor-format X-rows use the preserved `LEGACY_EDITOR_COLLECTION.md`, `LEGACY_EDITOR_MANIFEST.json`, and `EDITOR_COMPARISON_20261101.md`. Those research files are evidence inputs, not code/reuse licenses or redistributable fixtures.

“Pending fresh run” below is deliberate: the current build/test baseline is being established independently of older reports. Private corpus paths, retail hashes, compatibility settings, and runtime logs belong in private evidence records, never this public matrix. Checked-in tests use original or synthetic fixtures only.

## Maintenance procedure

1. Keep stable IDs. Add named subrows when a grouped family exposes materially different formats, transaction rules, or evidence requirements.
2. Record source revision and exact test command in the appropriate durable test/build documentation; put private paths, hashes, and runtime observations only in private evidence records.
3. Promote an evidence cell only after the corresponding artifact was actually exercised. A source path, old test count, compiler object, or successful import alone is insufficient.
4. Update the linked user, architecture, algorithm, format, and parity documentation in the same slice as behavior changes. Correct stale inventory statements rather than citing them as current proof.
5. A waiver names the row, exact excluded scope, rationale, and Andrei's explicit decision. “Not applicable” requires a technical format/scope boundary, not lack of time or missing interest.
6. No completion claim while any applicable row lacks required evidence, any required test is red, DroidWorks is only partially supported, or inaccessible historical tools are presented as tested.
